### INT-4R repair contract — sealed publication trust boundary

The first draft remains historical evidence. The repair has four states: **assembled → sealed → validated → active**. An assembler may create unpublished revisions and a candidate release; it cannot approve, validate or activate. A publisher seals the complete stored child set; a trusted validator issues an immutable receipt only after verifying actual evidence; a restricted activator changes the pointer with compare-and-swap. Runtime application credentials can read validated releases and pinned content but cannot mutate these publication records. Migration-owner credentials are never deployed with the application. Each privileged function has explicit execution grants and a fixed safe search path; application and assembler roles cannot disable triggers or issue validation receipts.

1. **Question seal.** `QuestionRevisionSeal` binds a recomputed full render/grade hash and ordered answer/media manifests to one revision and canonicalization version. The full hash covers prompt, points, hints, mode metadata, answer/trap/correctness state, ordered bindings and exact media identities. Editorial approval binds that hash; media rights bind exact bytes. Every child insert locks its question parent and rejects a seal already present. Seal creation takes the same lock, recomputes child manifests, verifies answer shape and existing exact receipt bindings, then inserts the seal. Updates/deletes/truncation remain prohibited. A later edit creates a new revision.
2. **Release seal.** `CatalogReleaseSeal` binds the recomputed root of canonical category revisions, crosswalks, source snapshots, sealed question memberships and proposed availability/evidence references. All release-owned child inserts lock their release parent and reject an existing seal; sealing locks the same parent and rejects an empty or inconsistent release. Category label/description/cover metadata needs an exact content-hash editorial approval and rights-cleared cover. A category is not public merely because its DTO fields are allow-listed.
3. **Validation receipt.** A restricted `CatalogValidationReceipt` references one exact seal/root, validator/policy and selector versions, source-evidence manifest hash, real fresh/repeat selector-run evidence for **every** advertised engine/mode/tier/modality, rights/editorial closure, and Huroof project/release/root/readiness identity. Its issuer must independently read the evidence, source membership and exact media bytes; a supplied 64-character string is not proof. Actual selector adapters used for validation must govern future selection. Unsupported/depleted combinations are omitted. A failed run produces private diagnostics, never a receipt.
4. **Activation and read.** `ActiveCatalogPointer` must reference the exact validated receipt as well as release/root. A restricted activation operation checks destination seal/receipt, expected old pointer and compatibility, writes an append-only event and changes exactly one pointer; first activation has an explicit expected-absent form. Public reads require complete pointer→receipt→seal→release lineage and emit only editorially accepted metadata and availability attested by that root. `sources.enta.available` derives from validated Enta availability, not snapshot existence. Mode/tier/modality vocabulary matches selectable UI/engine paths; preserve modality when it changes playability. Current Huroof pointer/root reads are transactional, but the validator additionally verifies approved count, actual category inventory/questions/media, rights overlay, selector runs and capability flags for the new Firebase project. The receipt binds capability flag state/version; the public reader rechecks current flags even if the release/root has not changed, suppressing affected modes on mismatch. Public reads and match admission also compare the receipt's selector/policy version with the *currently deployed* selector/policy, failing availability closed after an incompatible deploy. Admission rechecks current source identity before charging. Catalog observations are advisory, not a credit reservation.
5. **Game pins and migration.** New production writers require a validated release and complete question pins. Enforce parent/child pin equality with a database trigger using the parent `Game` row, while allowing null fallback only for historical pre-pin games. A trigger on `GameQuestion` alone is insufficient because it would allow a newly inserted unpinned `Game`. The migration must snapshot existing unpinned game IDs into an immutable `LegacyUnpinnedGame` eligibility table (or an equivalently DB-enforced cutover discriminator) populated only by the migration owner; the runtime role cannot add eligibility. A new `Game` insert must carry a validated release/pin and cannot opt into legacy eligibility. Legacy children are permitted only for those snapshotted IDs; a pinned parent requires both child pins and matching membership. A pinned reader must fail integrity checks on a missing revision, never fall back to mutable source content. Remove the redundant draft `Game(id,catalogReleaseId)` composite index/FK and its concurrent-index requirement if the trigger proof is accepted by Database. Preserve restrictive membership FKs. The receipt-to-release/root chain needs composite FK constraints; privileged functions need fixed safe search paths and explicit grants. Check consistent parent-before-child lock order. Before any SQL apply, review exact target row counts, role grants, lock behavior and a restore rehearsal on a separately isolated database.

## Source authority and release model

- Huroof keeps its immutable Firestore release publisher, active pointer/root and phase/role projections. Integration records the exact approved release ID/root and source question/media IDs; it cannot treat T44 draft/private rows or raw stored counts as reviewed playable content.
- Enta keeps mutable `Question`, `QuestionAnswer` and `StudentQuestion` as authoring sources only. A publication creates immutable `QuestionRevision` with source namespace/key, revision number, content hash, canonical category, original category/subject key, prompt, points, hints, modality, review and rights receipts. Its immutable `AnswerRevision` children carry ordered choices/list entries, correct/trap flags and points. `MediaRevision` records exact object key, byte hash, type and rights/provenance, rather than relying on a mutable external URL.
- Individual study content joins the same revision and rights model under its own source namespace. Study sessions pin selected revision IDs for consistency, consume no credit, and return prompts/choices without `correctIndex` or grading keys. This is a service-contract decision, not proof that existing study rows qualify.
- A versioned canonical crosswalk maps `(source namespace, source category ID)` to one canonical category key; published release membership explicitly declares eligible engine, mode and tier. Huroof and Enta may point to different approved revisions for the same category. One mutable active catalog pointer selects a fully validated immutable release. Retirement affects future selection only; match/session/history pins retain their revisions and media bytes.
- The concrete proposal uses immutable `CatalogRelease` source snapshots for the Enta revision manifest and exact Huroof Firestore release ID/root, per-revision membership, and a validated availability manifest by engine, mode, tier and modality. `ActiveCatalogPointer` is a singleton changed by compare-and-swap, so a stale publication cannot silently replace another approved release. Append-only editorial/rights receipts must bind exact content and asset hashes.
- New Enta matches initially write both legacy question ID and nullable `questionRevisionId`; revision-aware readers must use the pinned revision. Legacy fallback is limited to pre-pin historical rows. A published revision and its answer/media children cannot be updated or deleted by application roles. A referenced source question may be retired, never destructively deleted with match history.
- Add nullable `Game.catalogReleaseId` along with `GameQuestion.questionRevisionId` so new matches pin the complete approved catalog snapshot. Add study-session revision pins only with a reviewed study-session flow (or a separate additive table that remains unmounted until then).

### INT-4R3 private validator contract — 2026-10-02

**Decision and scope:** Astra medium planning plus Database and Security read-only reviews support a separate offline validator. This is a contract for implementation, not a receipt or publication approval. Its first supported source is a **single immutable Enta raw artifact per source snapshot** and text-only Enta CLASSIC at tiers 200/400/600. Every other engine, mode, media-dependent question and category cover stays unavailable until an exact extension is reviewed. The current issuer accepts caller-supplied evidence hashes and does not itself read artifacts or bytes; calling it with plausible hashes is prohibited until the validator independently proves the following closure.

1. **Canonical stored hashes.** Name the existing PostgreSQL 18.4 `jsonb::text` UTF-8 hash format `int4-pg-jsonb-v1`. The validator retrieves SQL payloads as `TEXT`, hashes those exact UTF-8 bytes and separately parses them for semantic checks. It never hashes a JavaScript parse/reserialize result. SQL question/category/release seal hashes and the issuer's source-summary hash retain their existing formula; a canonicalization change requires a new version and successor evidence, never reinterpretation of a historical seal.
2. **Enta artifact and snapshot.** `sourceRootSha256` is SHA-256 over the exact bytes of one privately archived raw source artifact (the current pilot uses `extraQuestions.json`); no newline, Unicode or whitespace normalization. The archive binds opaque artifact identity, byte length, digest, repository commit, source namespace/release ID and parser version. This initial format rejects a snapshot that requires multiple artifacts; a later version may define an artifact-manifest root after Database/Security review. `snapshotHash` is SHA-256 over UTF-8 PostgreSQL `jsonb::text` of a versioned `enta-source-snapshot-v1` object containing exact namespace, source-release ID, source root, parser version and **sorted selected members**. Each selected member binds a stable deterministic source ID, raw artifact digest, unambiguous category/one-based array locator, source category identity, complete normalized source payload and its `sourceContentHash` computed by the same canonical text rule. Unselected raw source rows are permitted but confer no catalog availability. Reject duplicate keys/IDs/locators, malformed bytes, unknown versions or ambiguous numeric/Unicode transforms before parsing or import. The pilot's source-file digest + category + one-based array index is provenance, not a random seed database ID. Preserve the raw artifact and manifest privately by digest; prove every selected member exists with exact bytes in that artifact, every selected member has exactly its specified DB revision/membership, and no DB membership exists outside the selected manifest. An editorial correction must bind source hash and final sealed content hash through explicit review evidence; it cannot silently replace source bytes. The existing issuer source-summary hash is only a digest of stored snapshot *identities* and cannot substitute for this external proof.
3. **Selector and editorial closure.** The offline validator replays the exact Enta CLASSIC tier selector implementation that the future authoritative match writer will call. Fresh and repeat samples must use disjoint pinned question revisions and eligible supply for each advertised category/tier/modality. It rejects any unmatched release membership, unsealed revision, changed answer, missing/held editorial or rights evidence, unsupported selector version, or mismatched output. Approved category label/description/cover hashes are checked independently; the initial text-only release therefore requires no cover. Record the selector build/version, inputs, outputs, seeds, exclusions and evidence digest in a private immutable report before any receipt issuance. A fixture or local seed count cannot certify playable content.
4. **Private media boundary.** The initial validator rejects question media, cover media and any media-dependent availability. A later bytes-only adapter may resolve an opaque content-addressed key through a server-owned immutable registry; it must never fetch or resolve arbitrary `MediaRevision.objectKey` text. Require exact digest/length, bounded read, MIME/magic agreement, actual decode, format/dimension/resource limits and rights receipt bound to exact bytes. Deny URL schemes, localhost, absolute/drive/UNC paths, backslashes, traversal, encoded separators, symlink/junction escape, swapped/truncated/corrupt/spoofed bytes and changed covers before any approval. Begin with a reviewed raster allowlist; SVG/audio/video need separate policies. No private bytes, answer or key enters public/player DTOs or logs.
5. **Privileges and ordered implementation.** Keep the reviewed R5 migration unchanged. In a separately reviewed additive R3 migration, grant only the distinct `catalog_validator` group `SELECT` on the proof/revision/receipt/seal/availability tables it must inspect and `EXECUTE` on the four existing invoker payload helpers if called; do not grant DML, activation, finance access, broad helper execution or PUBLIC access. Do not make a new `SECURITY DEFINER` reader. Verify a distinct validator login can recompute/read but cannot mutate, and runtime/assembler cannot issue a receipt. The deployed login membership must be inspected independently. Rollback revokes only these grants and disables the new validator policy, preserving immutable artifacts/seals/reports.

The draft catalog route remains unmounted, Huroof availability fails closed without deployed selector/project/release/root/capability attestation, and no content activation follows an isolated test. Denial fixtures must cover changed/missing/extra source members, forged roots, selector mismatch, stale/held rights, altered answers, path/URL attempts with zero I/O, changed media bytes and wrong role grants.

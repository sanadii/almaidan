## Authority and identity

A played bracket node has one server-controlled current attempt. A tournament owner and stable team IDs are authenticated through the new Firebase identity; names are display data, not identity. The server derives `logicalMatchId` from a versioned `(tournamentId, bracketNodeId, attemptNumber)` encoding. An attempt pins immutable participants, engine, admission, and room (Huroof) or Game (Enta). A browser cannot select an attempt number, attach an arbitrary admission, provide a winner as settlement proof, or create a free hosted match by setting a mode.

Additive new-format relations, preserving legacy rows/readers:

| Relation | Required boundary |
| --- | --- |
| `Tournament` | Firebase owner, immutable new-format discriminator, rules version, bracket version and champion team ID; historical owner/name fields remain read-only compatibility. |
| `TournamentMatch` | Stable node ID, version, team-ID slots, predecessor-slot links, current attempt, applied result and winner. Composite same-tournament FKs protect teams and topology. Seed and lock topology before paid attempts. |
| `TournamentMatchAttempt` | Server-allocated positive attempt number; unique `(tournamentId,bracketNodeId,attempt)`, logical match and admission; immutable participant/engine snapshot, state and reason; same-owner admission and exact node FKs. |
| `EngineMatchResult` | Append-only authoritative result version with attempt/admission/logical-match/engine/room-or-Game, predecessor hash, result hash, engine revision, participant mapping, outcome/winner/scores and correction evidence. Unique `(attemptId,resultVersion)`, no client DML. |
| `TournamentEvent` | Append-only idempotent attempt, result, correction, bye and conflict events with tournament sequence and before/after bracket versions. |

Do not duplicate an independently mutable room/Game association: derive it from the admission and require the attempt/result linkage to match. The exact FKs, triggers, role grants and legacy classification must be reviewed before even disposable migration application.

## Attempt allocation and billing

Authenticate the owner, validate the node and two distinct same-tournament participants, and resolve an existing idempotent request before a changed catalog pointer. Use Wallet → Admission/Reservation → Tournament → Node lock order for a new paid attempt. Under the node lock, reject an unresolved predecessor, blocked correction or live current attempt; allocate the next attempt number and its admission/reservation and attempt link atomically. Firestore provisioning/START_MATCH or Enta transactional start then follows the reviewed INT-5 protocol. A cancelled never-started attempt may be superseded only after durable cancellation and released hold. A replay of a started game is a new attempt and costs one credit; correcting its result is not a new match. Result import locks Tournament → Node and never acquires Wallet afterward.

Setup, seeding and byes have no admission or wallet effect. A bye advances only when topology proves one participant and one permanent empty seed, not when an opponent is pending. Bye events use stable IDs and versions; a bye node cannot accept a paid attempt or browser result.

## Engine result and bracket CAS

Huroof writes immutable, versioned final/corrected result evidence and a latest-version pointer in the **same Firestore transaction** as the reducer's final/corrected state. Evidence pins project, admission, logical match, room, tournament attempt, immutable engine-side-to-team mapping, authoritative game revision, result version, predecessor hash, outcome/winner and correction actor/reason. The engine derives the result from canonical state. Do not infer Huroof's winner from imported numeric scores. Enta uses the corresponding server-authoritative PostgreSQL Game result. Draws and unresolved outcomes fail closed for knockout advancement.

The importer uses project-pinned Admin reads or the Enta trusted transaction, checks the STARTED admission, exact participant mapping, predecessor chain and engine revision, then appends evidence. Identical version/hash is a no-op; same version/different hash is an integrity incident. A higher version with a missing predecessor remains pending; lower versions never replace higher. Evidence may arrive before PostgreSQL debit reconciliation and stays pending until the admission is COMMITTED.

To apply a result, lock Tournament and Node; require matching current attempt, participant snapshot, expected bracket/node version, committed admission and complete result chain. Update node winner/applied result, downstream predecessor-owned slot or champion, and append one event in a single PostgreSQL transaction. Concurrent semifinal imports serialize and fill distinct slots; CAS failure reloads instead of overwriting a stale slot. Round-robin standings derive from currently applied node results and recompute under tournament CAS so duplicate imports cannot add points twice.

## Corrections and downstream matches

Before a downstream attempt exists, a higher authoritative result version may replace its derived slot and increment versions atomically, while resetting only unplayed derived state. After any downstream attempt is allocated, preserve its participants, paid admission and historical results; record the correction and set `CORRECTION_BLOCKED`. Resume only through an explicit reviewed resolution: cancel/release an unstarted dependent attempt, or authorize a replay/superseding bracket decision. A started dependent match is immutable evidence; no automatic refund or participant reassignment. A delayed result from a superseded attempt remains audit history and cannot advance the current node.

**Open product policy:** round-robin tie-breaking, knockout draw resolution and downstream correction resolution need owner-approved rules before those cases are enabled. The new path must fail closed on unresolved ties instead of keeping a legacy implicit first-team win.

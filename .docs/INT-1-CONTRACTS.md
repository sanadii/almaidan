Firebase Admin SDK validates signature, issuer, audience/project ID, expiry and revocation according to action sensitivity. The only customer key is `(newProjectId, UID)`; upsert is concurrency-safe. Re-read server-controlled admin scope, never trust a name, email, browser role or stale JWT for elevation. For host/free grant/checkout require a non-anonymous Firebase principal whose email is currently verified (email/password or Google); guest join may use anonymous Auth. The one-time free grant is bound to UID and cannot be recreated by deleting app history.

| Principal | Allowed | Explicitly denied |
| --- | --- | --- |
| Public | Approved catalog/episode descriptions, sign-in entry | Draft content, answers, wallet, match actions, private media. |
| Anonymous Firebase guest | Huroof join, own player/audience projection and reconnection | Hosting, grant, checkout, admin, Enta judge/actor authority. |

| Enta actor QR | One match's assigned prompt/word view and permitted status action | Other answer keys, unrestricted question pool, host/admin actions. |
| Admin | Current server-side scoped content, support and finance operations with audit events | Direct raw balance overwrite or legacy shared-code impersonation. |

QR grants are opaque, high-entropy, stored hashed, short-lived, revocable and bound to match, role, permitted action and phase. Every use checks the live match/grant state and consumes only the needed projection. Every nested route first scopes child ID to authorized parent and account in the same query/transaction, including question open/answer/undo, lifelines, VAR and tournament results. Unauthorized/mismatched children return 404 without existence leaks. Same-origin browser API; any cross-origin support uses an explicit allowlist and never wildcard credentialed CORS. Legacy Enta public list/study endpoints must omit grading keys and unrevealed answers.

## Wallet and match admission (INT-012)

**PostgreSQL records:** `User(newProjectId,firebaseUid UNIQUE)`, `Wallet(userId UNIQUE, available/held materialized counters with nonnegative check)`, append-only `WalletEntry(originType,originId,effect UNIQUE, delta, timestamp, actor)`, `Admission(hostUid,engine,logicalMatchId,requestKey,requestHash UNIQUE as appropriate; state; room/game ID; content revision pins)`, append-only `AdmissionEvent` and uniquely keyed outbox/reconciliation jobs. Hold and ledger writes lock the wallet row; ledger is authority, counters are transactional projection. A free grant has a unique `(FREE_FIRST, UID, GRANT)` effect. Deleting history never deletes financial evidence. Store ID/key retention past room closure; a retry with the same key and different hash is a conflict.

**Huroof ordered transitions:** `REQUESTED → PG_RESERVED → FS_RESERVED → FS_STARTED → PG_COMMITTED`, or `FS_RESERVED → FS_CANCELLED → PG_RELEASED`. Firestore admission is durable and binds project, UID, engine, logical match, request hash, reservation ID, room and content release. `START_MATCH` and permanent cancellation both read/change `FS_RESERVED` in the **same Firestore transaction** with room state, so only one terminal outcome wins. If cancellation wins before provision or start, create/retain a tombstone that prevents late provision. A started room may be active while PG commit is retrying, but its hold remains locked, debit is eventually idempotent and reconciliation has an alert threshold; it can never be released as unused. Release requires a confirmed Firestore `CANCELLED` receipt. Firestore unavailable/ambiguous means hold remains pending, with support reconciliation; never infer cancellation from elapsed time. Duplicate reserve/start/commit/release returns the existing receipt. Invalid/stale starts do not transition or debit.

**Enta:** Server selects hosted versus individual study from route/operation authority, not a client-supplied `mode`. Successful hosted start creates the authoritative match, its revision pins and wallet debit atomically in PostgreSQL. Standalone list/acting/drawing and board-embedded list use the same hosted-match admission; rematch uses a new logical match/key. Tournament setup and byes are free; each played bracket node references exactly one paid engine match and its authoritative result. Concurrent or corrected results are versioned and checked against bracket advancement. Study uses a separate free session path; Huroof internal rounds, joins and reconnects are free. If content readiness fails, reject before reserving credit.

**Failure matrix to prove:** concurrent one-time grants/starts; two hosts racing last credit; duplicate request and mismatched hash; reserve succeeds but Firestore provision fails; delayed start versus expiry/cancel; lost responses/worker crash before and after each PG/FS transition; FS unavailable during reconciliation; started match PG commit retry; stale/invalid START; rematch and repeated tournament result; direct hosted API with `STUDENT`; active room deletion/history deletion. Exactly one started debit, no negative available balance and no cancellation after a durable start.

## Commerce, catalog and rollback (INT-013)

Purchase snapshot is immutable: credit quantity, exact integer minor-unit amount, ISO currency, package/discount terms, gift recipient, provider account/provider and provider reference. Settlement uses the purchase's stored provider and verifies reference/order/account/amount/currency from authenticated provider evidence; browser return parameters and webhook body are hints only. Webhooks require signed verification or provider lookup, unique event keys and one conditional fulfillment + ledger transaction. Zero-price orders still have explicit validated fulfillment. Gift redemption, coupon capacity, refunds, chargebacks and admin adjustments use conditional transaction updates and append-only entries; reversals are compensating events. Production startup/preflight fails if live gateway configuration is incomplete. Build/deployment never seeds the production database.

Catalog revision records carry canonical category, source namespace/ID, revision ID and content hash, review/rights/provenance receipt, supported engine/modes/tiers and media object hash. Public response omits drafts, grading keys, unrevealed answers and private asset URLs. Approval and supply checks are per mode/tier for a first and repeat match. Retiring a revision removes it from future selection while active/history matches continue to read the pinned immutable answer/media revision. Huroof's existing release pointer remains independently governed by its exact publication Gate; integration cannot turn T44 private rows public by category mapping.

**Migration/rollback order:** create new isolated Firebase/PostgreSQL environments; capture and restore-test backups; add nullable links/new tables and unique constraints; import only editorially accepted catalog revisions; deploy compatible readers; switch writers behind flags; validate data; tighten nonnull constraints; enable starts and checkout in staging first. After new payments, rollback disables new starts/checkout and reverts compatible code/catalog pointers while preserving wallet/admissions, callbacks and reconciliation. Restore a backup only into a separate instance for comparison; never overwrite the live ledger with an older database. Merchant and old-system financial-tail decisions remain release gates.

## Source boundary and current hazards

The combined `/api/v1` mounts health and account only. Imported Enta game, payment, gift, discount and admin routes remain unreachable. They cannot be mounted as the financial implementation: `games.ts` trusts client `mode=STUDENT`, reads `remainingGames` before an unguarded decrement, and allows nested child IDs to escape their parent; `payments.ts` checks paid status outside fulfillment, verifies through the current rather than stored provider and does not validate amount/currency/account; `gifts.ts` and discount capacity use check-then-write; legacy admin writes raw balances. Huroof's current callable can create/start rooms without a PostgreSQL admission. Production MyFatoorah currently defaults to a test host if its live URL is omitted. These are verified source findings, not evidence of an exploited live deployment.

## PostgreSQL proposal for exact schema review

- The new wallet belongs to the unique `FirebaseIdentity.id` for the fresh project and UID, not the optional legacy `User` link. The legacy `remainingGames`, `unlimitedGames`, `Float` prices and `Purchase` rows never authorize new spending or fulfillment. No historical balances are imported by default.
- `Wallet` holds materialized nonnegative `available`, `held` and `debt` counters plus a version. Append-only `WalletEntry` records available/held/debt deltas, origin, effect, actor and timestamp, with a unique origin/effect key. All counter and entry writes occur under the same wallet row lock and transaction. The sum of entries must reconcile to counters. The one-time free grant has a unique effect keyed to the Firebase identity and can be issued only to a currently verified non-anonymous UID. Deleting account history does not delete financial evidence.
- `Admission` binds identity, engine, logical match ID, request key/hash, room or game ID, content release pins and state. Enforce **separate** unique keys for `(Firebase project, UID, engine, logical match ID)` and `(Firebase project, UID, request key)`; a single four/five-column composite is insufficient. The canonical request hash binds engine, operation, logical match, content release/root, host and material configuration. Same key plus different hash conflicts; a changed key cannot purchase/start the same logical match twice. One `Reservation` belongs to one admission; append-only `AdmissionEvent` and uniquely keyed outbox jobs record transitions and retries. Unique nonnull room/game references prevent double association. A wallet with debt cannot start new paid matches. New hosted routes derive operation type server-side; client `STUDENT` or `unlimitedGames` never exempts a hosted match.
- `CheckoutOrder` is a separate immutable financial snapshot: identity, provider **and merchant account**, package/quantity, integer minor-unit amount, ISO currency, discount version/terms, gift recipient, purpose and request hash. `PaymentAttempt` uniquely binds provider/account/reference; append-only `ProviderEvent` deduplicates callbacks; `Fulfillment` is unique per order. A verified settlement locks the order and wallet and conditionally creates one credit grant or one gift entitlement in the same transaction. A browser return is only a hint. The provider adapter must return authenticated order, account, reference, exact amount and currency evidence; a Boolean `paid` is insufficient.
- `GiftEntitlement` has one order, a unique code hash and a conditional one-time recipient claim that posts one ledger effect. Reserve discount capacity under a locked coupon/version row at checkout and retain enough capacity for a late valid settlement; terminal failure/refund policy determines release. `OrderAdjustment` plus compensating ledger entries handle refunds, chargebacks and admin corrections, never history edits or raw balance overwrites. Chargeback after spending may create recorded debt; the exact partial-refund and redeemed-gift liability rules remain product decisions before real money.
- Database constraints and permissions must enforce unique effects, nonnegative counters, immutable published financial rows and restrictive history references. Application checks alone are insufficient. Review exact generated SQL and lock/row-count impact on the isolated target before applying it. Retain old legacy tables for compatibility; do not seed or migrate local demo balances into the fresh wallet.

## Match admission and reconciliation

1. Validate fresh-project Firebase token, current verified email, UID, content readiness and idempotency hash. A PostgreSQL transaction locks the wallet and reserves exactly one available credit for a new hosted logical match. A retry returns the same admission; insufficient credit is rejected before game creation.
2. The Express service uses its fresh-project Firebase Admin identity to provision a durable Firestore admission and room **after** the PostgreSQL hold, binding reservation ID, project/UID, engine/logical match ID, request hash, room ID and pinned release. Direct Huroof create/start callables must require this admission; a browser cannot provision or forge it. `START_MATCH` and permanent `CANCELLED` contend on the **same Firestore transaction** with the room; a cancellation tombstone prevents late provision/start. A started room is never treated as cancellable for credit release.
3. The PostgreSQL-side reconciler confirms `STARTED` or `CANCELLED` by reading the exact Firestore admission/room through the server's project-pinned Admin SDK; client-supplied status and forwarded user tokens are never proof. A verified `STARTED` record causes an idempotent PostgreSQL commit of the held credit. A verified `CANCELLED` tombstone permits idempotent release. If Firestore is unavailable or the outcome is ambiguous, leave the hold pending and alert/reconcile. Expiry alone is not cancellation. Lost responses and worker crashes must be recoverable from durable state and outbox events.
4. Enta hosted start, including standalone list/acting/drawing, validates content and atomically creates the authoritative match, revision pins, one debit and committed admission in PostgreSQL. Invalid/stale starts cost nothing. Huroof internal rounds, joins, reconnects, tournament setup/byes and individual study remain free; a rematch or played bracket match has a new paid logical match identity.
5. All direct Huroof callables and same-origin APIs must enforce this admission server-side before a room can start. A UI disabled state is not an authorization boundary. A tournament result references its one paid engine match and authoritative result; corrections and concurrent submissions are versioned.

### INT-5B Huroof admission protocol — Astra medium design, 2026-10-02

This is an implementation contract for later exact Database/Security/financial Gate review, not authorization to change live Huroof callables. A new hosted Huroof logical match has one PostgreSQL admission, one one-credit reservation and a **stable server-assigned room ID** before Firestore provisioning. Its immutable intent binds Firebase project/UID and internal owner, engine, logical match/request keys, catalog and Huroof release/root/selector/capability policy, room ID, and optional predecessor match or tournament slot. PostgreSQL enforces separate owner/request-key and owner/engine/logical-match uniqueness; an identical retry resolves its stored intent before inspecting a rotated pointer.

Firestore `paidAdmissions/{admissionId}` stores the same bindings and durable `RESERVED`, `STARTED` or `CANCELLED` state. `STARTED` and `CANCELLED` are irreversible financial outcomes. **Only their competition in one Firestore transaction decides whether a held credit commits or releases.** Expiry, a missing room, a failed response or Firestore unavailability cannot by themselves release a hold. The room stores immutable admission/owner/configuration pins; client rules deny admission writes and financial-proof reads.

| PostgreSQL | Firestore | Required behavior |
| --- | --- | --- |
| `HELD` | absent | Retry idempotent provisioning or create a full-binding cancellation tombstone; never infer refund from absence. |
| `HELD` | `RESERVED` | Valid authenticated owner start and trusted cancellation may race on the same document. |
| `HELD` | `STARTED` | Reconcile one `COMMIT`; gameplay continues if PostgreSQL is temporarily unavailable. |
| `HELD` | `CANCELLED` | Reconcile one `RELEASE`; room cannot become playable. |
| `COMMITTED` | `STARTED` | Terminal billing state; later rounds, reconnects and completion do not charge. |
| `RELEASED` | `CANCELLED` | Terminal refund state; retry returns the original cancellation. |
| Any | absent, mismatched or contradictory proof after provisioning | Keep financial state pending, stop new transitions and alert; no guessed correction. |

**Sequence:** The admission API verifies the current Firebase owner, server-derived hosted operation and content readiness, then locks Wallet → Admission → Reservation in PostgreSQL, persists the hold, stable room ID and provisioning outbox job atomically, and releases all SQL locks before Firestore I/O. A project-pinned internal worker provisions the admission, room, host membership, code and projections in one Firestore transaction; code collision may change the code, never room/admission IDs. The existing production `createRoom` entry must return only that exact already provisioned admission or be retired; demo exemptions stay isolated. `START_MATCH` authenticates the host and, in one Firestore transaction, reads room/member/intent receipt/admission/readiness, requires exact pins plus a valid lobby transition, then writes the game transition, admission `STARTED`, start evidence, receipt and projections together. Stale/invalid/content-held starts cost nothing. An identical start retry returns the old receipt even if the match progressed. Cancellation reads the same admission and room transactionally: absent admission creates a permanent full-binding tombstone; `RESERVED` atomically closes the lobby and becomes `CANCELLED`; `STARTED` refuses cancellation. A missing admission with an existing playable room is an integrity incident. Tombstones and financial proof remain available through reconciliation.

An internal reconciler claims a short fenced PostgreSQL outbox lease, releases that row lock, reads Firestore through the pinned Admin project, validates full bindings and authoritative start/cancel evidence, then locks Wallet → Admission → Reservation and posts the unique terminal ledger effect/event. Duplicate workers, lost responses and crashes at each boundary are no-ops or pending holds, never double charge/refund. Do not perform network/SQL side effects inside a retried Firestore transaction callback. Retain the room and admission proof until an independently reviewed archival protocol exists.

**Continuation and linkage:** Guard every direct production callable/alias, QA permit, rematch and tournament start; App Check supplements but never replaces host identity and admission checks. Internal Huroof rounds and joins reuse the started admission. A rematch gets a new logical match/admission/room with immutable predecessor. A played tournament slot derives logical identity from tournament, bracket node and server-controlled attempt; byes/setup are free and client retries cannot increment attempt. The authoritative result is bound to admission/room/logical match/game revision and written with final Firestore game state; PostgreSQL imports versioned results by direct Admin reads and advances brackets conditionally. User-supplied winner data cannot settle or advance a match. Completion does not govern billing: started abandoned matches remain consumed.

**Required isolated proof:** Firebase emulators plus restricted PostgreSQL roles must exercise last-credit and duplicate starts; delayed provision versus tombstone; both start/cancel race orders; stale intent/content hold; every reserve/provision/start/cancel/reconcile crash or lost response; Firestore outage at expiry; wrong project/UID/room/pin; direct callable and QA bypass; rematch/new debit; rounds/reconnect zero debit; result retries/corrections and concurrent bracket versions; ledger reconciliation. Rollback disables new reservation/provision/start but retains active joins, terminal reconciliation and an admission-aware Functions version. Reverting to unrestricted old `createRoom`/start code is unsafe.

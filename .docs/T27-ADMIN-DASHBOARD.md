# T27 — Firebase administration dashboard repair

## Authority and current evidence

2026-09-17: user requests a plan and complete dashboard functional/design repair with Firebase connection. Implementation and scoped backend deployment necessary for the dashboard are authorized. Existing production content, permissions, immutable releases and unrelated work must be preserved.

The current dashboard calls authenticated Firebase Functions in me-central1, but lists `adminQuestionDrafts` and `adminCategoryMetadata` rather than active release content. Its overview reports draft counts alone. Active content is stored behind `runtime/activeRelease`; current counts must be read live, never copied from historical docs. The current shell has oversized controls, weak hierarchy and generic record/JSON rendering. Auth login works, but the shell currently checks only Google status despite supported verified password authentication. Graphify's existing graph is historical; direct source inspection is authoritative.

## Decisions and boundaries

- D27.1: Display published content and authoring drafts as distinct sources. Default question/category browsing shows the actual active Firebase release, with server-side bounded category filtering, stable pagination and detail views. Never copy immutable published records into drafts merely to populate the UI.
- D27.2: Keep all reads behind existing callable principal/capability/category-scope enforcement. No browser direct privileged Firestore access, security-rule weakening or answer exposure in public APIs.
- D27.3: Preserve existing mutation gates. Make disabled actions understandable and avoid presenting blocked publication/settings actions as working. Existing supported draft/review/room/user workflows remain accessible according to capabilities and backend availability. This task does not invent signing authority or enable globally staged mutations.
- D27.4: Reuse approved DESIGN-DNA/T18 palette, Arabic typography and themes; adapt composition to administration without replacing brand authority.
- D27.5: Include on-demand image/video question and answer preview through an authenticated admin callable. Reuse the existing immutable-media generation/hash/MIME validation pattern; resolve only stored question bindings, accept no client object path, cap bytes at 1MB, return inline content rather than making Storage public. Unsupported/missing/oversize media gets an explicit recoverable state. Gate covers this additional read boundary before deployment.

## VISUAL CONTRACT

Product mood and visual concept: calm, professional Arabic content administration for الخلية, using the approved cobalt/navy/ice identity. Dominant focal point and scan order: page title and primary task, live inventory/status, compact filters, records/detail. Information density: 5/10 desktop and 4/10 mobile. Desktop composition: stable right sidebar around 230px, compact top header, fluid workspace with generous gutters and aligned tables; mobile: accessible collapsing navigation, stacked filters and readable record cards without page overflow. Typography: existing IBM Plex Sans Arabic, 26–32px page headings, 16px body, 13–14px metadata, normal Arabic tracking, tabular counts and isolated LTR identifiers. Palette/surfaces: approved cobalt primary, ice/white light surfaces and navy dark equivalents, restrained cyan active states, subtle borders; status always has text. Spacing/shapes: 8/16/24/32px rhythm, modest 12–18px panel corners, compact 40–44px controls, no giant full-width actions for ordinary table tools. Icons/imagery: consistent simple outline icons with Arabic labels; category artwork only where already available and relevant; no decorative dashboard hero. States: explicit loading skeleton/status, retry errors, true zero-data vs filtered-empty, stale/pagination handling, keyboard focus, truthful disabled reasons, usable forms/detail panels. Motion: short 120–200ms transitions, reduced-motion support, no ambient animation. Anti-patterns: nested oversized cards, giant headings, raw JSON as primary detail, fake metrics/charts, unexplained zeros, hidden filters, or frontend-only permission checks.

## Risks, impact and rollback

Firestore queries may require indexes; prefer existing document-ID ordering and bounded equality queries. Release switching must not mix pages silently; bind cursors/details to a release or reset safely. Category-scoped admins must never receive unauthorized content/counts. Existing mutation gates may restrict actions: expose the reason, do not silently bypass. Production impact is authenticated read APIs only; no schema/data migration or active release pointer writes planned. Rollback the exact scoped function/source changes using task-start evidence, preserving unrelated working-tree work; retain published content intact. Do not use broad Git restoration.
